Get started with NETWATCH NG

Via the official APT repository

Recommended method: signed repository published on GitHub Pages, netwatch-ng package 2.0.0-1 (stable suite, main component, amd64 architectures). Works on Debian and antiX.

sudo install -d -m 0755 /usr/share/keyrings

curl -fsSL https://sudomarc.github.io/NETWATCH/public.key \
  | sudo gpg --dearmor --yes -o /usr/share/keyrings/netwatch-ng-archive-keyring.gpg

echo "deb [arch=amd64 signed-by=/usr/share/keyrings/netwatch-ng-archive-keyring.gpg] https://sudomarc.github.io/NETWATCH/ stable main" \
  | sudo tee /etc/apt/sources.list.d/netwatch-ng.list

sudo apt update && sudo apt install netwatch-ng

cd NETWATCH
python -m pip install -e .

What NETWATCH NG monitors

Every module is implemented and tested. The TUI delegates all business logic to the command layer: validation, ownership checks and SSH host verification remain in the core.

netwatch-ng — Devices

        

        

          

            
Device discovery

            
Continuous passive ARP/NDP discovery, operator-triggered Nmap on an authorized target or subnet, evidence-based identification (neighbors, Nmap, local OUI table) with source and confidence level displayed. Inventory export to JSON or CSV.

          

          

            
Wi-Fi intelligence

            
Radio inventory and access-point survey via the Aircrack-ng suite (`airmon-ng`, `airodump-ng`). Monitor mode is an explicit operator action: the interface carrying the default route is never forced, and the TUI restores the adapter on exit.

          

          

            
Firewall

            
IPv4/IPv6 forwarding blocking (FORWARD chain) via NETWATCH rules marked as owned. A pre-existing chain of the same name is rejected rather than modified. Read-only preview and explicit confirmation before each reset.

          

          

            
Network diagnostics

            
Default gateway ping, DNS resolution and route trace from the TUI, with bounded activity log. Each result is dated, qualified (success, warning) and viewable in the Logs screen.

          

          

            
Traffic management

            
Egress/ingress rate policing via `tc` clsact filters: packets above the configured rate are dropped. The root qdisc is never replaced — behavior is stated as-is, without an HTB shaping promise.

Security-first design

        
The principles that govern every NETWATCH NG screen.

      

      

        

          
« Identification is evidence-based: neighbors, Nmap and local OUI table. Every device attribute remains labeled with its source and confidence level. »

          
Evidence-based identification

        

        

          
« Block and unblock operate only on the NETWATCH chain explicitly marked as owned. A pre-existing chain with the same name is rejected, never modified. »

          
Owned Netfilter chains

        

        

          
« No destructive action is ever a one-key action: scope, target and owned resources are displayed before confirmation. »

          
Explicit confirmations

        

        

          
« With `--dry-run`, no write occurs — not iptables, not tc, not ARP, not state files — while read-only validation describes what would happen. »

FAQ

      

        

          On which systems does NETWATCH NG run?
          
NETWATCH NG is a Linux-only tool. The TUI requires Python 3.10+ (standard library `curses`, no third-party dependency). Debian package builds are validated in CI for Debian 12 and 13.

        

        

          Are root privileges required?
          
Control operations — firewall, Wi-Fi monitor mode, traffic policing, reset — require root. Passive discovery, interface inspection and diagnostics work without elevation, with separate state directories by privilege.

        

        

          Is Wi-Fi monitor mode dangerous for my connection?
          
Putting an interface into monitor mode interrupts the Wi-Fi connection on that interface: it's an explicit action, preceded by a warning and confirmation. The survey refuses to force the interface carrying the default route, and the TUI restores the adapter on exit. `airmon-ng check kill` is never run automatically.

        

        

          Which optional tools enrich NETWATCH NG?
          
Nmap for active discovery and service identification, the Aircrack-ng suite for Wi-Fi inventory and survey, `dsniff`/`arping` for ARP support on the 1.x line. Missing tools are detected at runtime and the corresponding capabilities are announced as unavailable.

        

        

          What is the difference between NG and the legacy Bash 1.x line?
          
NETWATCH NG is the Python 3 rewrite with an exclusive full-screen TUI (dashboard, devices, firewall, diagnostics, persistent settings, bounded activity log). The legacy Bash 1.x scripts remain available as the historical CLI surface; the 1.x capability table in the README describes that line, not the rewrite.

        

        

          Is there a stable 2.0.0 version?
          
Yes. Version 2.0.0-1 is published on the official signed APT repository (stable/main, amd64) and accompanied by the GitHub release `v2.0.0`. Installation is a single command after repository configuration; the from-source method remains available for contributing.

        

        

          Can I contribute or report a security issue?
          
Yes. See `CONTRIBUTING.md` for contributions and `SECURITY.md` for responsible disclosure. Regression tests (Bash and Python) and the pseudo-terminal E2E suite run locally without real network scanning.
